# LOMA 1.0 conformance suite

*English · [Italiano](README.it.md)*

This folder is the operational definition of "conforming compiler" ([SPEC.md §2 and §17](../SPEC.md#2-conformance)). It is for anyone writing a LOMA compiler in any language.

## Content

- `valid/NAME.loma`: a valid file, with
  - `NAME.mid`: the expected MIDI bytes;
  - `NAME.events.json`: the expected events in canonical JSON;
  - `NAME.sha256`: the SHA-256 of the MIDI file.
- `errors/NAME.loma`: an invalid file, with
  - `NAME.errors.json`: the expected list of `{"code", "line"}`, in the order in which they must be reported.
- `run.py`: the checking program.

The names of the valid cases start with a number: `0xx` language 0.1, `2xx` 0.2, `3xx` 0.3, `4xx` 1.0. The error cases start with the code they check; those that start with `X_` check the order of the errors and the absence of cascading errors, and the `X_mixed_` ones the files that have syntax and content errors together (SPEC §13.1).

## Usage

The compiler under test must offer three commands:

```
CMD compile FILE -o OUT        status 0, writes the MIDI file
CMD expand FILE --json         status 0, canonical JSON on standard output
CMD check FILE --json          status 1 if there are errors, JSON array of errors on standard output
```

```
python3 conformance/run.py --cmd "python3 -m loma"
python3 conformance/run.py --cmd "node js/loma.js"
python3 conformance/run.py --cmd "./my-compiler" --first-error-only
```

With `--first-error-only`, only the first error of the invalid files is compared: it is the minimum that the specification requires (MUST). Without the option the complete list is compared (SHOULD).

## Origin of the expected files

The expected files are generated by the reference compiler with `tools/make_conformance.py`. Two exceptions give the suite a fixed point that does not depend on the compiler:

- `valid/010_minimal.mid` matches the bytes worked out by hand in SPEC.md §16.1;
- the tempo values of `valid/020_tempo_ramp` (100, 92, 85, 77, 70 BPM) and of the controller ramps are verified by hand in the tests.

The hashes of the cases that already existed in 0.1 are pinned in the tests: they cannot change.

Regenerating the expected files is a change of the specification: it must be done only on purpose.
